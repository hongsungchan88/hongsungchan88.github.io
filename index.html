개인 프로젝트 · 2026.04 – 2026.06

실시간 티켓 예매 시스템

코드 보기 ↗
Spring Boot 4.0.5Java 21 Spring SecurityJPA JWTMySQL Apache JMeter

다수의 사용자가 동시에 좌석을 예매하는 상황을 가정하고 동시성 제어를 직접 구현한 콘서트·공연 좌석 예매 시스템입니다. JPA Optimistic Lock으로 Race Condition을 해결하고, JMeter 부하 테스트로 실제 동작을 검증했습니다.

문제 해결JMeter 동시 요청 1,000건으로 정합성 붕괴를 재현하고 Optimistic Lock으로 막았습니다. 다시 측정해 보니 경쟁에서 진 요청이 500으로 응답하고 있어 409로 바꿨고 그 뒤 드러난 MySQL 데드락은 쿼리 실행 순서를 바꿔 해결했습니다. 서버 도달 기준 500 응답은 478건에서 0건이 됐습니다.

주요 문제 및 해결 과정

  • 동시성 이슈 해결 및 테스트 — JMeter로 1,000개의 동시 요청 부하 테스트를 진행해, 락 미적용 상태에서는 하나의 좌석에 동시 요청 수만큼 예매가 중복 성공하는 정합성 붕괴를 직접 재현했습니다. JPA @Version 기반 Optimistic Lock 적용 후에는 최초 커밋된 트랜잭션만 성공하고 나머지는 버전 충돌 예외로 처리되어, 동일 조건에서 중복 예매 0건을 검증했습니다.
  • Optimistic Lock 채택 이유 — 예매 시스템 특성상 좌석 선점(Update)보다 조회(Read) 비율이 압도적으로 높을 것으로 예상해, DB에 직접 락을 거는 Pessimistic Lock 대신 애플리케이션 단에서 버전을 관리하는 Optimistic Lock을 채택해 조회 요청까지 잠금을 기다리는 상황을 피했습니다.
  • 경쟁에서 진 요청이 500으로 응답 — 수정 전 측정에서 서버에 도달한 479건 중 478건이 500이었습니다. 낙관적 락 예외는 커밋 시점에 발생해 서비스 코드 안에서 잡을 수 없어서 @RestControllerAdvice로 409 Conflict를 돌려주게 했습니다. 좌석은 한 명만 가질 수 있어 재시도는 넣지 않았습니다.
  • MySQL 데드락 — 409 처리 후 재측정에서 500이 1건 남았고 서버 로그에 Deadlock found가 찍혀 있었습니다. 원인을 따라가 보니 예매 ID가 IDENTITY라 INSERT가 먼저 실행되며 외래키 검사로 좌석 행에 공유 락이 걸리고 커밋 때 좌석 UPDATE가 배타 락을 기다리면서 트랜잭션끼리 엇갈렸습니다. holdSeat() 직후 saveAndFlush로 좌석 UPDATE를 먼저 실행하게 바꾼 뒤 서버 도달 399건 기준 성공 1·409 398·500 0을 확인했습니다.
  • 미결제 좌석 복구 버그 — 5분 미결제 자동 취소 로직이 releaseSeat() 대신 reserveSeat()를 호출해 좌석이 판매 완료로 남던 문제를 고치고 단위 테스트로 검증했습니다.
  • 버전 마이그레이션 이슈 해결 — Spring Boot 4.x 도입 시 3.x와 달라진 설정·의존성 충돌을 공식 마이그레이션 가이드를 참고해 해결하고 변경 사항을 문서로 정리했습니다.

주요 구현 사항

  • Spring Security와 JWT를 활용한 사용자 인증 및 API 접근 권한 제어
  • Spring Data JPA를 활용한 공연·좌석 관리 REST API 설계

주요 문제 및 해결 과정

  • AI 모델 응답 파싱 실패 — 확장 사고(thinking) 블록 대응 — Claude 모델을 리뷰 모델로 연동하는 과정에서 모델이 응답 content 배열 맨 앞에 thinking 블록을 추가하면서 content[0]을 텍스트로 가정했던 기존 로직이 빈 응답을 받아 리뷰 결과 JSON 파싱이 실패했습니다. content 배열 전체를 순회해 type: "text"인 블록만 이어 붙이는 방식으로 수정해, 여러 AI 모델(Claude/OpenAI/Gemini/Groq)을 한 인터페이스로 안정적으로 전환할 수 있게 했습니다.
  • GitHub 웹훅 재전송으로 인한 PR 리뷰 중복 생성 — GitHub 웹훅이 같은 이벤트를 재전송(retry)하면서 동일 PR에 대해 리뷰가 중복 생성되는 문제가 있었습니다. PR의 head_sha를 추적해 이미 처리된 커밋이면 재실행을 건너뛰도록 수정해 중복 리뷰·중복 AI 호출을 방지했습니다.

주요 문제 및 해결 과정

  • 소셜 로그인 토큰 URL 노출 — 소셜 로그인 후 JWT를 URL 쿼리스트링으로 넘기고 있었습니다. 쿼리스트링은 서버 로그·브라우저 기록·Referer에 남을 수 있어 토큰 전달 위치를 URL fragment(#)로 옮겼습니다.
  • 배포 환경 이메일 인증 장애 — AWS 차단 포트 진단 — 로컬에서 정상 동작하던 이메일 인증이 배포 환경에서만 실패했습니다. AWS가 차단하는 포트로 SMTP를 설정한 것을 확인하고 허용 포트로 변경·재배포하여 정상 동작까지 검증했습니다.
  • OpenAI 응답 형식 안정화 — response_format: json_object 강제 지정으로 API 레벨에서 형식을 차단하고 시스템 프롬프트에 응답 스키마와 종목별 무승부 허용 규칙을 명시했습니다.
  • API 비용 제어 — DB 캐싱 전략 — 경기당 예측 결과를 DB에 저장해 캐시가 있으면 재호출하지 않는 구조로, 경기당 1회 호출로 비용을 제한했습니다. 야구는 캐시 유효성을 검사해 무효면 다시 생성합니다.
